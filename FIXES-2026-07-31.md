Eight issues found during a read-through of the backend, all verified against the
live site at `turathya.com` before and after the change. Nothing has been
deployed yet — see [Deploying](#deploying) at the end.

## 1. Bids were accepted on lots that had already ended — Critical

**What was wrong.** `routes/bids.ts` selected `l.*` and then `a.start_date,
a.end_date` without aliases. Both tables have columns by those names, and
node-postgres lets the last one win — so `lot.end_date` was silently the
*auction's* end date. The lot's own dates were unreachable.

This became wrong when migration `20260422_add_lot_dates_make_auction_dates_optional`
moved timing from the auction level to the lot level ("categories no longer
require timing — products do"). `bids.ts` was never updated to follow.

**Impact, measured on live data.** All 3 auctions run until 2027; all 18 lots'
own `end_date` values had already passed. The frontend reads `lot.end_date` and
showed every lot as ended, while the API happily accepted bids on all 18. The
lot's `status` was never checked either, so `sold`, `unsold`, and `withdrawn`
lots also accepted bids.

**What changed** — [`src/routes/bids.ts`](zauction-backend/src/routes/bids.ts)

- Aliased the auction columns so lot columns are no longer shadowed, and dropped
  the two auction date columns entirely since nothing reads them now.
- Added a lot `status` check (validation 1).
- Replaced the window check with one that mirrors the `lot_has_auction`
  expression in `routes/lots.ts` — the same rule the frontend uses to decide
  whether to show bidding UI. A lot is biddable only if it has its own
  `start_date`, `end_date`, and a `starting_bid > 0`.
- Narrowed the row lock from `FOR UPDATE` to `FOR UPDATE OF l`. The old form
  also locked the auction row, serializing every bid across an entire category.

**Verification.** Replaying both versions of the logic against all 18 live lots:

```
OLD logic accepted: 18   ← bids allowed on lots that closed weeks ago
NEW logic accepts :  0
breakdown          : {'ended': 16, 'not an auction item': 2}
```

The 16 "ended" lots are exactly the 16 with `lot_has_auction: true`, and the 2
"not an auction item" lots are exactly the 2 with `lot_has_auction: false`.
Backend and frontend now agree lot-for-lot.

> One thing to be aware of: this means bidding is now genuinely closed on all 18
> lots, which is what the site already showed. If any of them were meant to still
> be live, their `end_date` needs extending — that is a data change, not a code
> one.

## 2. Password-reset OTP was brute-forceable — Critical

**What was wrong.** `/forgot-password/reset` compared a 6-digit OTP with no
attempt counter, no lockout, and — the important part — the pending record was
**not discarded on a wrong guess**. It survived until it expired or succeeded.
With no rate limiting anywhere in the app, the ~900k code space could be walked
in parallel inside the validity window. Success = resetting any account's
password knowing only its phone number.

The same gap left `/login` open to password brute force, and let
`/forgot-password/request-otp` be used to pump unlimited WhatsApp messages at
arbitrary numbers — a good way to get the business number banned.

**What changed**

- [`src/routes/auth.ts`](zauction-backend/src/routes/auth.ts) — added an
  attempt budget (`MAX_OTP_ATTEMPTS = 5`) to both the registration and reset
  flows. The pending record is deleted once spent, so the code dies with it.
  This is the hard stop, and it works regardless of how many IPs an attacker
  rotates through.
- Switched both OTP comparisons to `crypto.timingSafeEqual`.
- [`src/middleware/rateLimit.ts`](zauction-backend/src/middleware/rateLimit.ts)
  — new, dependency-free fixed-window limiter. Applied as:

  | Endpoint | Limit |
  |---|---|
  | `register/request-otp`, `forgot-password/request-otp` | 5/hour **per phone** + 20/hour per IP |
  | `register/verify-otp`, `forgot-password/reset` | 15 per 10 min per IP |
  | `login` | 10 per 15 min per IP |

  Per-phone limiting stops one victim being flooded from many IPs; per-IP stops
  one host flooding many numbers.

- [`src/server.ts`](zauction-backend/src/server.ts) — added
  `app.set('trust proxy', 1)`.

> **⚠️ Needs checking on the VPS.** The rate limiter keys on `req.ip`. Behind
> nginx that is `127.0.0.1` for everyone unless nginx forwards the real address.
> Confirm the `/api` proxy block contains:
>
> ```
> proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
> ```
>
> Without it every visitor shares one bucket and legitimate users will start
> getting 429s. The per-phone OTP limit and the attempt budget are unaffected —
> those don't depend on IP.

I chose a small in-house limiter over `express-rate-limit` deliberately: the app
runs as a single process, which is exactly what that library's default memory
store handles, and this avoids adding a dependency that a deploy could miss. If
the backend is ever run multi-instance, this needs to move to Redis — per-process
counters would hand each instance a full quota.

## 3. SQL injection in three admin update endpoints — High

**What was wrong.** All three did `Object.keys(req.body)` → `` `${field} = $n` ``
with no allowlist. Postgres cannot parameterize identifiers, so while the
*values* were safe, the **column names came straight from the request body**.
That hands the caller the left-hand side of a `SET` clause.

- [`admin/lots.ts`](zauction-backend/src/routes/admin/lots.ts)
- [`admin/auctions.ts`](zauction-backend/src/routes/admin/auctions.ts)
- [`admin/categories.ts`](zauction-backend/src/routes/admin/categories.ts)

All three sit behind `requireAdmin` (I checked — all six admin routers are
correctly guarded), so an admin token was needed first. But it turned "can edit a
lot" into "can read and write the whole database", e.g. writing
`(SELECT password_hash FROM users LIMIT 1)` into a publicly readable field.

**What changed** — new
[`src/utils/buildUpdate.ts`](zauction-backend/src/utils/buildUpdate.ts) exporting
`buildUpdateSet()` plus explicit column allowlists, now used by all three routes.
Unknown keys are dropped and reported back as `rejected_fields` rather than
reaching SQL.

**Verification.**

```
malicious payload ->
  setClause: "title" = $2
  rejected : [ "description = (SELECT password_hash FROM users LIMIT 1), title" ]

real admin payload ->
  fields kept: 10 of 10
  rejected   : []
```

While building the allowlist I found the admin panel sends `is_featured`, which
is a real column on the production `lots` table but appears in no migration and
not in `schema.prisma` (see #5). Had I built the list from the Prisma schema
alone, this fix would have silently broken the featured toggle. The allowlists
are built from the live table columns.

## 4. `current_bid` / `bid_count` were never maintained — Medium

**What was wrong.** Placing a bid inserted a row into `bids` and updated nothing
else, despite both `README.md` and `ARCHITECTURE.md` describing an `UPDATE lot`
step. Only the admin "remove top bidder" path maintained those columns.

The lot **list** endpoint returns them via `l.*`; the lot **detail** endpoint
computes `MAX(amount)` in a subquery. So listings and the lot page would have
disagreed the moment real bidding started. Currently masked — every lot has 0
bids, so the column reads `NULL` and looks correct by accident.

**What changed** — [`src/routes/bids.ts`](zauction-backend/src/routes/bids.ts)
recomputes both columns from the `bids` table inside the same transaction as the
insert, and the socket broadcast now sends those authoritative values instead of
just the incoming bid amount. The migration in #5 backfills any existing rows.

## 5. Production schema drift — Medium

**What was wrong.** Three columns existed only on the production database:

| Column | Used by | In `schema.prisma`? | In a migration? |
|---|---|---|---|
| `lots.show_in_gallery` | `admin/lots.ts`, `admin.js` | No | No |
| `lots.is_featured` | `admin/lots.ts`, `admin.js` | No | No |
| `lots.image_data`, `auctions.image_data` | several routes | Yes | No |

`start:prod` runs `prisma migrate deploy`. Rebuilding the database from
migrations would have produced a schema where admin lot creation failed
immediately.

**What changed**

- New migration
  [`20260731000000_reconcile_production_schema_drift`](zauction-backend/prisma/migrations/20260731000000_reconcile_production_schema_drift/migration.sql).
  Written to be idempotent (`ADD COLUMN IF NOT EXISTS`), so it is a no-op against
  the live database and correct against a fresh one. It also converges the two
  boolean flags on `NOT NULL DEFAULT false` and backfills the #4 columns.
- `schema.prisma` gains `showInGallery` and `isFeatured` on `Lot`.

## 6. Pending-OTP maps grew without bound — Medium

Expired entries were only dropped when that exact phone number was looked up
again, so abandoned registrations accumulated for the life of the process. Added
a 5-minute sweeper over both maps in `auth.ts`.

Still worth knowing: these are **in-memory**, so every pending registration and
reset is wiped on restart or redeploy. Fine for a single process; moving them to
a table or Redis is the real fix if that ever becomes a problem.

---

## 7. Unauthenticated socket broadcast — Low

`socket/handlers.ts` had a `new-bid` handler any anonymous client could emit to
make the server fan out a broadcast to a lot room. It performed no database
write, so no bid could be forged, but it was a free amplification handle — and it
read the stale `current_bid` column, so it broadcast wrong numbers anyway.

Removed. Nothing in the frontend emits it (verified), and `POST /api/bids`
already emits the authoritative `lot-updated` after the transaction commits.
Socket connections stay unauthenticated on purpose — lot rooms carry public data
and requiring auth would break anonymous browsing.

---

## 8. No upper bound on bid amount — Low

`isFloat({ min: 0 })` against a `Decimal(10,2)` column meant anything over
99,999,999.99 became a database error surfacing as a 500. Bound added to match
the column.

## 9. Admin panel: editing an auction threw a `ReferenceError` — Critical

This is the issue the client reported. It is a pre-existing production bug,
unrelated to fixes 1–8 (none of which were deployed at the time).

**What was wrong.** `editAuction()` in `frontend/js/admin.js` ended with:

```js
window._adminRestorePlacementMode(lot);   // ← `lot` does not exist here
```

`_adminRestorePlacementMode` is the *lot* placement-mode helper (gallery /
auction / both). The call had been pasted into `editAuction`, where the only
object in scope is `auction` — and it was **missing from `editLot`**, where
`lot` is defined and where it belongs. There is no global `lot` in `admin.js` or
in any other script loaded by `admin.html` (checked all five).

**Impact — the sequence the client would have hit.**

1. Admin clicks **Edit** on an auction.
2. The form fields populate, `editingId` is set, and the button changes to
   "Update Auction" — all of that runs *before* the throw.
3. The `ReferenceError` fires, control jumps to `.catch()`, and a red
   **"Failed to load auction details"** toast appears. The form never scrolls
   into view.
4. The admin reasonably concludes editing failed — but the form is silently
   still in **edit mode**, because `editingId` was already set.
5. They then type in what they intend to be a *new* auction and submit. Because
   `editingId` is still populated, it issues `PATCH /admin/categories/<id>` and
   **overwrites the existing auction instead of creating a new one**.

Net effect from the client's side: "I can't create auctions," plus an existing
auction quietly getting overwritten. Nothing except a successful save ever
cleared `editingId` — there is no cancel button.

**Reproduced** by loading the live `admin.js` from `turathya.com` and calling
`editAuction()` against a stubbed DOM:

```
=== LIVE admin.js (what the client is running) ===
Failed to load auction for editing: ReferenceError: lot is not defined
   ERROR TOAST SHOWN: "notifications.failedLoadAuctionDetails"
   form.dataset.editingId = "A1"      ← form left in edit mode

=== FIXED admin.js ===
   scrollIntoView reached (edit mode fully entered)
   form.dataset.editingId = "A1"
```

**What changed** — [`frontend/js/admin.js`](frontend/js/admin.js)

- Removed the misplaced call from `editAuction()`.
- Added it to `editLot()`, where `lot` is in scope — so editing a lot now
  correctly restores its gallery/auction/both placement mode, which it never did.
- Both `.catch()` handlers now reset `editingId` and the submit button label, so
  a future error can never strand the form in edit mode and cause a silent
  overwrite.

**Cache-busting** — [`frontend/pages/admin.html`](frontend/pages/admin.html)
loaded `admin.js` with no version string, and nginx sends no `Cache-Control`
header for it (only `ETag` / `Last-Modified`), so browsers cache it
heuristically. Bumped to `admin.js?v=4` so the fix actually reaches the client
without a manual hard-refresh.

## Deploying

`npx tsc --noEmit` and `npm run build` both pass. I did not start the server
locally — `.env` points at the production database and the live-auction notifier
starts on boot, so a local run could fire real WhatsApp messages. Verification
should happen on the VPS.

1. **Back up the database first.** The migration is idempotent but it does write.

2. **Apply the migration.** Check the recorded migration state before choosing a
   path — if the production database was created from `schema.sql` rather than by
   Prisma, `_prisma_migrations` may be empty and a plain `migrate deploy` will try
   to replay `20260209223213_init` against existing tables:

   ```bash
   psql "$DATABASE_URL" -c "SELECT migration_name, finished_at FROM _prisma_migrations ORDER BY finished_at;"
   ```

   If earlier migrations are recorded, `npm run start:prod` applies this one
   normally. If the table is empty or partial, apply the SQL directly (it is safe
   to run against the live schema) and then record it:

   ```bash
   psql "$DATABASE_URL" -f prisma/migrations/20260731000000_reconcile_production_schema_drift/migration.sql
   npx prisma migrate resolve --applied 20260731000000_reconcile_production_schema_drift
   ```

3. **Check the nginx `X-Forwarded-For` header** — see the warning under #2. This
   is the one change that can degrade real users if the config is missing.

4. **Build and restart** the backend.

5. **Smoke-test after restart:**

   ```bash
   curl -s -o /dev/null -w "%{http_code}\n" https://turathya.com/api/auctions
   ```

   Then, signed in as an approved user, confirm a bid on an ended lot returns
   `400 "Bidding has ended for this lot"` instead of succeeding, and that editing
   a lot in the admin panel still saves the featured and gallery toggles.

## Not addressed

Deliberately left alone — flagging rather than fixing, since they are either
judgment calls or larger pieces of work:

- **`/api/auctions` returns 493 KB.** Auction and lot images are base64 in
  `image_data` and ship in the list payload — 387 KB for a single auction. Every
  homepage visit downloads that. Wants a move to file/CDN storage, or at minimum
  excluding `image_data` from list responses.
- **The nginx config is unversioned.** The clean-URL 301s, the crawler
  interception for WhatsApp previews, and the `/api` proxy exist only on the VPS.
  Worth copying into the repo next time we log into Hostinger.
- **No `helmet`**, so no security response headers.
- **Stale hosting configs** — `render.yaml`, both `netlify.toml`s,
  `frontend/wrangler.toml`, `frontend/_redirects` all describe deploy targets
  that are not production. The Render backend returns 503.
- **`Zauction_20260416.zip` (74 MB) is committed**, and `.git` is 147 MB.
- **Routes use raw `pg` while migrations use Prisma**, so the schema has two
  sources of truth. That split is what let #5 happen.
